# 008 — T5: статическая недостижимость + нулевые сэмплы вместо только динамики

## Problem

`DEAD_OR_UNREACHABLE_CODE` (`t5_redundant_checks.py:22-42`) считает метод мёртвым кодом,
если `className STARTS WITH 'com.example' AND sampleCount = 0`. Это чисто динамический сигнал
и он путает два разных утверждения:
- метод **статически недостижим** ни из одной точки входа (реальный мёртвый код);
- метод достижим, но **не был задет именно этим тестовым прогоном** (пробел в покрытии, не дефект).

Без статического графа эти два случая неразличимы, а `SUBMISSION.md` штрафует именно за
заявление находки там, где её нет ("ложная находка... — штраф").

## Goal

Построить статический граф вызовов от объявленных точек входа (Spring
`@Controller`/`@RestController`/`@Service` public-методы, `main`, тестовые методы) и требовать
от `DEAD_OR_UNREACHABLE_CODE` **оба** условия: статическая недостижимость И нулевые
рантайм-сэмплы.

## Non-goals

- Не строить универсальный статический анализатор для произвольных фреймворков — точки входа
  определяются по стандартным Spring-аннотациям и `public static void main` / JUnit `@Test`,
  этого достаточно для проектов, подпадающих под таксономию хакатона.
- Полный, интерпроцедурный dataflow-анализ не нужен — только достижимость по графу вызовов
  (кто кого статически может вызвать), без учёта условий/веток.

## Approach

1. Новый модуль `skill/scripts/static_callgraph.py`:
   - парсит `.class`-файлы проекта (через `javap -c -p`, byte-code уровень — надёжнее, чем
     регулярки по исходнику) и извлекает для каждого метода список вызываемых методов
     (по `invokevirtual`/`invokeinterface`/`invokestatic`/`invokespecial` инструкциям);
   - строит граф `Set[Method] × Set[(Method, Method)]`;
   - находит точки входа: методы с аннотациями `@RequestMapping`/`@GetMapping`/`@PostMapping`/
     `@RestController`-класса, `public static void main`, методы с `@Test`;
   - вычисляет `reachable = BFS/DFS от всех точек входа`.
2. `analyze_t5` (`t5_redundant_checks.py`) получает доступ к `reachable`-множеству (передаётся
   как параметр или вычисляется один раз и кэшируется рядом с БД) и меняет условие:
   `sampleCount = 0 AND method NOT IN reachable`.
3. Методы с `sampleCount = 0 AND method IN reachable` (достижимы, но не протестированы) — не
   выбрасываются, а формируют отдельный, менее критичный тип `UNTESTED_REACHABLE_CODE`
   (`LOW`, не заявляется как дефект, годится только для `checked_but_not_an_issue` с пояснением
   "не покрыто текущим набором тестов, не мёртвый код").

## Files touched

- `skill/scripts/static_callgraph.py` (новый файл)
- `skill/scripts/analyzers/t5_redundant_checks.py` (изменить `analyze_t5`, добавить параметр
  `reachable_methods`)
- `skill/scripts/analyze_anomalies.py` (прокинуть построение `reachable` перед вызовом `analyze_t5`)

## Acceptance criteria

- [ ] На проекте с реально недостижимым приватным методом (не вызывается никем, включая тесты)
      `static_callgraph.py` не включает его в `reachable`.
- [ ] На методе, достижимом из контроллера, но не покрытом ни одним тестом (сэмплов 0, но
      статически достижим) — `DEAD_OR_UNREACHABLE_CODE` **не** срабатывает; вместо этого
      появляется `UNTESTED_REACHABLE_CODE`.
- [ ] Regression: на существующих demo-сервисах (`NPlusOneService` и т.д.) все публичные
      REST-эндпоинты и вызываемые из них методы попадают в `reachable`.
- [ ] Явный юнит-тест на резолюцию точек входа: класс с `@RestController` и методом с
      `@GetMapping` корректно распознаётся как entry point.
