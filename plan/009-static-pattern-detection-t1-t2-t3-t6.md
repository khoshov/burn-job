# 009 — Статические детекторы для T1/T2/T3/T6 вместо матчинга по именам

## Problem

Самые "заточенные под песочницу" правила (прямая цель штрафа из `TASK/SUBMISSION.md` за
"правила, захардкоженные под конкретный проект") — это:
- T6 `N_PLUS_ONE_QUERIES` (`t6_db_queries.py:22-43`): матчит `methodName CONTAINS 'findBy'/'getEmployees'`
  — `getEmployees` буквально имя метода из demo-проекта, на `control`-проекте с другим доменом
  это правило не сработает никогда.
- T3 `FULL_FETCH_FOR_EXISTENCE_CHECK` (`t3_improper_func_usage.py:47-53`): матчит
  `b.methodName CONTAINS 'findAll'/'getEmployees'/'findUserById'` — та же проблема.
- T2 `QUADRATIC_NESTED_LOOP` (`t2_inefficient_algos.py:50-56`): матчит только конкретную форму
  `forEach/map/iterator` → `List.contains` — не находит вложенные циклы в целом.
- T1 (все правила) — только `save`/`StringBuilder` по имени, никакого структурного анализа
  дублирования кода.

## Goal

Добавить статические (AST/аннотации) детекторы, которые находят структурные признаки этих
антипаттернов независимо от имён классов/методов конкретного проекта.

## Non-goals

- Не заменять существующие CPU-graph правила полностью — они остаются как быстрый динамический
  сигнал (переименовать/понизить приоритет — задача [010](010-rule-config-externalization.md)).
  Здесь добавляются **новые**, дополнительные правила.
- Не реализовывать общий межпроцедурный dataflow — только паттерны, локализуемые в пределах
  одного метода + аннотаций JPA-полей.

## Approach

Новый модуль `skill/scripts/static_pattern_detectors.py`, использующий byte-code/AST-инфраструктуру
из [003](003-source-mapping.md)/[008](008-static-callgraph-reachability-t5.md):

1. **T6 — N+1 по JPA-аннотациям**: найти поля с `@OneToMany`/`@ManyToMany` без `fetch = EAGER`
   и без `JOIN FETCH` в соответствующем репозитории; проверить, вызывается ли геттер такого поля
   (`.getX()`/`.size()`/`.iterator()`) внутри цикла (`for`/`forEach`/stream-терминал) по
   результату `findAll()`/`findBy...()`. Это структурная сигнатура N+1, работающая на любых
   именах сущностей.
2. **T3 — избыточная выборка ради проверки существования**: dataflow в пределах метода —
   если результат вызова репозитория присваивается переменной, и единственное использование
   этой переменной — `!= null`, `.isEmpty()`, `.size() ==/> `, `.isPresent()` — это
   `FULL_FETCH_FOR_EXISTENCE_CHECK` независимо от имени метода.
3. **T2 — вложенные циклы общего вида**: AST-обход тел методов на предмет цикла (`for`/`while`/
   stream-`forEach`) внутри другого цикла, где внутренний цикл итерирует по коллекции,
   зависящей от переменной внешнего цикла (эвристика O(n²) по структуре, не по конкретному
   `List.contains`).
4. **T1 — дублирование кода**: сравнение нормализованных AST-поддеревьев тел методов
   (переменные обезличиваются) на структурное сходство выше порога — классический
   CPD/duplicate-code подход, применяется к парам методов в одном модуле.

Результат каждого детектора — список аномалий в том же формате, что и Cypher-based анализаторы
(`taxonomy_id`, `category`, `type`, `severity`, `caller`/`callee` как file:line вместо
class.method, `description`), чтобы `analyze_anomalies()` мог их объединить с графовыми находками
без изменения нижестоящего кода ([004](004-findings-json-generator.md), `non_defects.py`).

## Acceptance criteria

- [ ] На demo-коде (`NPlusOneService`) N+1-детектор находит `getDepartmentsSubOptimal` по
      структурному признаку (аннотация `@OneToMany` + вызов в цикле), не зная имени `getEmployees`
      заранее (детектор не должен содержать строку `"getEmployees"` в своём коде).
  - [ ] На тестовом коде с другими именами (например, переименовать `getEmployees` → `getStaff`
      в копии проекта для теста) детектор всё ещё срабатывает — это прямая проверка от штрафа
      "захардкожено под проект".
- [ ] T3-детектор находит `FullEntityFetchService`-подобный код по факту "результат используется
      только для проверки", без списка конкретных имён методов.
- [ ] T1-детектор дублирования находит хотя бы одну пару структурно похожих методов на
      demo-проекте (или явно возвращает пустой список, если такой пары нет — не обязан находить
      искусственно).
- [ ] Ни один из новых детекторов не содержит в коде литералов вида `"getEmployees"`,
      `"findUserById"`, `"NPlusOneService"` и подобных сандбокс-специфичных имён.
