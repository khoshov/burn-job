# 011 — Относительные пороги и сравнение прогонов по runId

## Problem

Все правила используют абсолютные пороги (`count > 50`, `sampleCount > 100`, `count > 5` и т.д.),
зависящие от длительности прогона и интервала сэмплирования (`interval=1ms` в нашем тесте дал
11216 сэмплов за 8 секунд — при другом `interval`/длительности те же паттерны дадут другие
абсолютные числа и либо не пройдут порог, либо завалят его шумом). Поле `runId` в схеме
(`CALLS.runId`, и новые узлы из [002](002-graph-schema-extension.md)) существует, но ни один
анализатор не сравнивает данные между разными `runId` — а именно такое сравнение даёт самое
сильное доказательство (`evidence.before/after`), которое `TASK/SUBMISSION.md` требует для
уровня `hard`.

## Goal

1. Заменить абсолютные пороги на пороги относительно `total_samples` прогона (уже считается
   при инжесте, `percent` уже есть на `CALLS`) везде, где это применимо.
2. Добавить переиспользуемую функцию differential-сравнения двух `runId` (baseline/candidate),
   которую может использовать любой анализатор или генератор findings.json.

## Non-goals

- Не менять то, как физически получаются два прогона (это ответственность вызывающего кода/
  нагрузочного теста — данная спека только про то, что делать с двумя `runId`, уже находящимися
  в одной базе).

## Approach

1. Аудит всех порогов в `graph_rules.yaml` (после [010](010-rule-config-externalization.md);
   если 010 ещё не сделана — правки вносятся прямо в `analyzers/t*.py`) — каждый абсолютный
   порог `count > N` получает эквивалент `percent > X` (например `count > 50` на профиле с
   несколькими тысячами сэмплов — это обычно 0.5-2%; конкретные X подбираются по фактическому
   распределению на demo-профиле, чтобы сохранить текущую чувствительность правил).
2. Новая функция `skill/scripts/differential_analysis.py::compare_runs(conn, baseline_run_id, candidate_run_id) -> list`:
   - для каждого метода/ребра, присутствующего в обоих `runId`, считает разницу в
     `count`/`percent`/`bytes` (для `Allocation`)/`retainedCount` (для `RetainedObject`);
   - возвращает список `{method, metric, before, after, delta_pct}`, отсортированный по
     убыванию `delta_pct` — это и есть готовый источник `evidence.before/after`.
3. Подключить `compare_runs` в [004](004-findings-json-generator.md): если в БД есть хотя бы
   два `runId` (например baseline "до фикса" и candidate "после фикса", как уже делает demo
   вручную через REST-эндпоинты `/bad` vs `/good`), `evidence.before/after` в `findings.json`
   заполняется реальными числами из `compare_runs`, а не приблизительными сэмплами одного прогона.

## Files touched

- `skill/scripts/rules/graph_rules.yaml` / `analyzers/t*.py` (пороги → проценты)
- `skill/scripts/differential_analysis.py` (новый файл)
- `skill/scripts/export_report.py` (использовать `compare_runs`, когда доступно ≥2 `runId`)

## Acceptance criteria

- [ ] Прогон одного и того же `.collapsed`-файла с половинным и удвоенным числом сэмплов
      (искусственно продублировать/проредить строки для теста) даёт одинаковый набор находок
      после перехода на процентные пороги (было бы разным при абсолютных).
- [ ] `compare_runs()` на двух прогонах одного и того же метода с разной нагрузкой возвращает
      корректный `delta_pct`, знак совпадает с направлением реального изменения.
- [ ] `findings.json`, сгенерированный при наличии двух `runId` в базе, содержит нескруглённые,
      воспроизводимые числа в `evidence.before`/`evidence.after` (не placeholder).
- [ ] Regression: на единственном `runId` (как было до этой спеки) пайплайн не падает — просто
      не использует `compare_runs` и оставляет однопрогонные приблизительные evidence-числа
      из [004](004-findings-json-generator.md).
