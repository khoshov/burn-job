## 🚨 T1. Избыточные вычисления и операции

### 📋 Суть и механизм
Категория включает ситуации, когда одна и та же работа выполняется многократно (дублирование запросов, вычисление значений в цикле, вызов одиночных операций сохранения вместо пакетных).

### 💡 Варианты исправлений

#### 🔹 Вариант 1.1: Пакетная обработка вместо итеративных операций (JDBC Batching)
Накопление объектов в коллекцию и выполнение одной пакетной операции вместо $N$ индивидуальных вызовов.

```java
// ❌ ДО (T1): Поштучное сохранение в цикле
for (Employee emp : employees) {
    employeeRepository.save(emp); // N сетевых запросов
}

// ✅ ПОСЛЕ (Вариант 1.1): Накопление и единый вызов saveAll()
employeeRepository.saveAll(employees);
```
* **Плюсы:** Уменьшение количества сетевых round-trips в $batch\_size$ раз.
* **Минусы:** Требует настройки `hibernate.jdbc.batch_size` и использования совместимой стратегии ID (`SEQUENCE` / manual ID).

#### 🔹 Вариант 1.2: Мемоизация и кэширование повторных вычислений (`@Cacheable`)
Сохранение результатов «дорогих» операций в память для повторного использования.

```java
// ✅ ПОСЛЕ (Вариант 1.2): Кэширование справочных данных
@Cacheable(value = "departments", key = "#id")
public DepartmentDto getDepartmentById(Long id) {
    return departmentRepository.findDtoById(id);
}
```
* **Плюсы:** Мгновенный возврат результата ($O(1)$) без обращения к базе или повторного вычисления.
* **Минусы:** Накладные расходы на валидацию и инвалидацию кэша при изменении данных.

#### 🔹 Вариант 1.3: Вынос инвариантов из циклов (Loop Invariant Hoisting)
Вынос вычислений, не зависящих от итерации, за пределы цикла.

```java
// ❌ ДО: Вызов метода / выборка на каждой итерации
for (Order order : orders) {
    BigDecimal rate = exchangeRateService.getCurrentRate(); // Лишний вызов N раз
    order.calculateTotal(rate);
}

// ✅ ПОСЛЕ: Вынос за пределы цикла
BigDecimal rate = exchangeRateService.getCurrentRate();
for (Order order : orders) {
    order.calculateTotal(rate);
}
```

## 🚨 T2. Неэффективные алгоритмы

### 📋 Суть и механизм
Использование алгоритмов с неоптимальной временной сложностью ($O(N^2)$ вместо $O(N)$ или $O(N \log N)$), например, вложенные циклы для поиска соответствий.

### 💡 Варианты исправлений

#### 🔹 Вариант 2.1: Преобразование списков в Hash-структуры ($O(N^2) \to O(N)$)
Использование `HashMap` или `HashSet` для мгновенного поиска по ключу вместо линейного сканирования списков.

```java
// ❌ ДО (T2): Вложенный цикл O(N * M)
for (Order order : orders) {
    for (User user : users) {
        if (order.getUserId().equals(user.getId())) {
            order.setUserName(user.getName());
        }
    }
}

// ✅ ПОСЛЕ (Вариант 2.1): Индексация в Map O(N + M)
Map<Long, User> userMap = users.stream()
    .collect(Collectors.toMap(User::getId, Function.identity()));

for (Order order : orders) {
    User user = userMap.get(order.getUserId());
    if (user != null) {
        order.setUserName(user.getName());
    }
}
```
* **Плюсы:** Драматическое снижение времени выполнения на больших объемах данных.
* **Минусы:** Дополнительные затраты памяти на создание `Map`.

#### 🔹 Вариант 2.2: Делегация сортировки и агрегации в СУБД
Перенос сортировки ($O(N \log N)$) и группировки из кода Java на уровень SQL (B-Tree индекса).

```java
// ❌ ДО: Сортировка всей коллекции в Java Heap
List<Order> sorted = orderRepository.findAll().stream()
    .sorted(Comparator.comparing(Order::getCreatedAt))
    .toList();

// ✅ ПОСЛЕ (Вариант 2.2): Использование SQL ORDER BY + Index
List<Order> sorted = orderRepository.findAllByOrderByCreatedAtDesc();
```

#### 🔹 Вариант 2.3: Бинарный поиск / Двууказательные алгоритмы (Two Pointers)
Поиск элементов за $O(\log N)$ в отсортированных массивах вместо последовательного обхода $O(N)$.

## 🚨 T3. Неправильное использование функций и API

### 📋 Суть и механизм
Загрузка тяжелых сущностей и графов объектов в случаях, когда от них требуется только одно скалярное поле, факт существования или количество строк.

### 💡 Варианты исправлений

#### 🔹 Вариант 3.1: Использование Spring Data Projections (Interface / DTO)
Выборка только необходимых колонок вместо полных `@Entity`.

```java
// ✅ ПОСЛЕ (Вариант 3.1): Interface Projection
public interface EmployeeNameProjection {
    Long getId();
    String getFirstName();
    String getLastName();
}

List<EmployeeNameProjection> findProjectedBy();
```
* **Плюсы:** СУБД генерирует `SELECT id, first_name, last_name FROM employees`, пропуская незадействованные колонки. Сущности не загружаются в PersistenceContext.
* **Минусы:** Выборка является Read-Only.

#### 🔹 Вариант 3.2: Специализированные методы `existsById()` и `count()`
Замена загрузки объектов на специальные SQL-агрегаты.

```java
// ❌ ДО: Загрузка всей сущности ради проверки наличия
boolean exists = employeeRepository.findById(id).isPresent();

// ✅ ПОСЛЕ (Вариант 3.2): SQL SELECT COUNT(...) > 0
boolean exists = employeeRepository.existsById(id);
```

#### 🔹 Вариант 3.3: Использование `Slice<T>` вместо `Page<T>`
Отключение подсчета общей суммы страниц, когда это не требуется по интерфейсу (бесконечный скролл).

```java
// ✅ ПОСЛЕ (Вариант 3.3): Убирает тяжелый SELECT COUNT(*)
Slice<OrderDto> findByStatus(String status, Pageable pageable);
```

## 🚨 T4. Ошибки в раскладке данных

### 📋 Суть и механизм
Неоптимальное размещение данных в памяти или БД: выгрузка гигантских текстовых/бинарных полей (`@Lob`, BLOB/CLOB) при частых запросах списков.

### 💡 Варианты исправлений

#### 🔹 Вариант 4.1: Вертикальное шардирование сущностей (Vertical Partitioning)
Вынос тяжелых полей в отдельную сущность с ленивой связью `@OneToOne(fetch = FetchType.LAZY)`.

```java
// ✅ ПОСЛЕ (Вариант 4.1): Легкая базовая сущность
@Entity
public class Employee {
    @Id private Long id;
    private String name;

    @OneToOne(mappedBy = "employee", fetch = FetchType.LAZY)
    private EmployeeDetail detail; // LOB хранится в отдельной таблице
}
```
* **Плюсы:** Базовый поиск по таблице `Employee` не читает из диска тяжелые блобы.
* **Минусы:** Требуется дополнительная таблица в СУБД.

#### 🔹 Вариант 4.2: Ленивая гидрация LOB-полей через Bytecode Enhancement
```java
@Lob
@Basic(fetch = FetchType.LAZY)
private String detailedBiography;
```
* **Плюсы:** Тяжелое поле загружается из БД только при явном вызове `getDetailedBiography()`.
* **Минусы:** Требует подключения плагина компиляции Hibernate Bytecode Enhancer.

#### 🔹 Вариант 4.3: Использование компактных DTO Records и примитивов
Замена тяжелых Wrapper-классов (`Long`, `Double`) на примитивы в критичных структурах или использование Java `record`.

## 🚨 T5. Избыточные проверки и блоки кода

### 📋 Суть и механизм
Дублирование логики проверок на нескольких слоях приложения, мертвые ветви кода, выполнение проверок условий в Java вместо SQL `WHERE`.

### 💡 Варианты исправлений

#### 🔹 Вариант 5.1: Единая точка декларативной валидации (Bean Validation)
Замена ручных `if (x == null)` на аннотации `@NotNull`, `@Size` на уровне DTO.

#### 🔹 Вариант 5.2: Перенос бизнес-фильтрации в SQL-условие `WHERE`
```java
// ❌ ДО: Выборка всех строк и проверка статуса в Java
List<Order> active = orderRepository.findAll().stream()
    .filter(o -> "ACTIVE".equals(o.getStatus()))
    .toList();

// ✅ ПОСЛЕ (Вариант 5.2): Фильтрация на стороне СУБД
List<Order> active = orderRepository.findByStatus("ACTIVE");
```

#### 🔹 Вариант 5.3: Делегация проверок целостности СУБД-ограничениям (`CHECK`, `FK`)
Перенос проверок уникальности и диапазонов на уровень constraints базы данных.

## 🚨 T6. Ошибки в запросах к базе данных

### 📋 Суть и механизм
Проблема $N+1$ запросов, отсутствие индексов, отсутствие пакетной вставки, выполнением множества единичных запросов в цикле.

### 💡 Варианты исправлений

#### 🔹 Вариант 6.1: JPQL / HQL `JOIN FETCH` (Решение проблемы N+1)
Загрузка родительской сущности и ее связей за $1$ SQL-запрос.

```java
// ✅ ПОСЛЕ (Вариант 6.1): 1 SQL запрос с соединением таблицы
@Query("SELECT DISTINCT d FROM Department d LEFT JOIN FETCH d.employees")
List<Department> findAllWithEmployees();
```
* **Плюсы:** Снижает число запросов с $1 + N$ до 1.
* **Минусы:** Ограничения при пагинации коллекций.

#### 🔹 Вариант 6.2: Использование `@EntityGraph`
```java
@EntityGraph(attributePaths = {"employees"})
List<Department> findAll();
```

#### 🔹 Вариант 6.3: Пакетная гидрация через `@BatchSize` / `default_batch_fetch_size`
```properties
spring.jpa.properties.hibernate.default_batch_fetch_size=50
```
* **Плюсы:** Сокращает вызовы с $1 + N$ до $1 + \lceil N / 50 \rceil$, безопасно при нескольких коллекциях.

#### 🔹 Вариант 6.4: Пакетная вставка через Spring `JdbcTemplate.batchUpdate()`
```java
jdbcTemplate.batchUpdate(sql, new BatchPreparedStatementSetter() { ... });
```
* **Плюсы:** Ускоряет bulk insert в 10–20 раз, обходит ограничения стратегии `IDENTITY`.

#### 🔹 Вариант 6.5: Индексация колонок в СУБД
Добавление B-Tree / Partial индексов под условия фильтрации и сортировки.

## 🚨 T7. Утечка памяти (Memory Leak)

### 📋 Суть и механизм
Удержание объектов в памяти без возможности их очистки Garbage Collector'ом (неограниченные `Map`/кэши, нерелизящиеся сущности в `PersistenceContext` при обработке гигантских наборов данных).

### 💡 Варианты исправлений

#### 🔹 Вариант 7.1: Периодическая очистка Persistence Context (`clear()` / `detach()`)
Освобождение объектов из 1st-level cache при пакетных операциях.

```java
// ✅ ПОСЛЕ (Вариант 7.1): Сброс сессии каждые 50 элементов
for (int i = 0; i < list.size(); i++) {
    entityManager.persist(list.get(i));
    if (i % 50 == 0) {
        entityManager.flush();
        entityManager.clear(); // Сброс ссылок для GC
    }
}
```

#### 🔹 Вариант 7.2: Использование Bounded LRU Cache с вытеснением
Ограничение максимального размера кэша через Caffeine / Ehcache.

```java
// ✅ ПОСЛЕ (Вариант 7.2): Ограничение максимального размера кэша
Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(10, TimeUnit.MINUTES)
    .build();
```

#### 🔹 Вариант 7.3: Использование Hibernate `StatelessSession`
Массовые операции записи/чтения без сохранения состояния в памяти.

## 🚨 T8. Перерасход памяти (Memory Bloat)

### 📋 Суть и механизм
Загрузка избыточных объемов данных в память (выгрузка таблицы из 500 000 строк для отображения первой 10-ки).

### 💡 Варианты исправлений

#### 🔹 Вариант 8.1: СУБД-пагинация через `Pageable`
```java
Page<OrderDto> findByStatus(String status, Pageable pageable);
```

#### 🔹 Вариант 8.2: Keyset / Cursor Pagination (Пагинация по монотонному ключу)
```java
@Query("SELECT o FROM Order o WHERE o.id > :lastId ORDER BY o.id ASC")
List<Order> findNextPage(@Param("lastId") Long lastId, Pageable pageable);
```
* **Плюсы:** Время отклика $O(1)$ для любых глубин пагинации.

#### 🔹 Вариант 8.3: Потоковая выгрузка больших наборов (Stream / ScrollableResults)
```java
@QueryHints(@QueryHint(name = HINT_FETCH_SIZE, value = "1000"))
Stream<Order> streamAllByStatus(String status);
```

## 🚨 T9. Избыточная нагрузка на CPU

### 📋 Суть и механизм
Бесполезная трача тактов процессора на частые операции конкатенации строк, компиляции регулярных выражений или тяжелую синхронную обработку.

### 💡 Варианты исправлений

#### 🔹 Вариант 9.1: Использование `StringBuilder` / примитивных типов
Замена конкатенации строк (`+`) в цикле на `StringBuilder`.

#### 🔹 Вариант 9.2: Кэширование скомпилированных шаблонов `Pattern`
```java
// ❌ ДО: Pattern.compile() внутри горячего метода
boolean match = str.matches("^[A-Z0-9]+$"); 

// ✅ ПОСЛЕ (Вариант 9.2): Статическая предкомпиляция
private static final Pattern PATTERN = Pattern.compile("^[A-Z0-9]+$");
boolean match = PATTERN.matcher(str).matches();
```

#### 🔹 Вариант 9.3: Асинхронное выполнение фоновых задач (`@Async` / Virtual Threads)
Вынос тяжелой фоновой работы из основного HTTP-потока.
