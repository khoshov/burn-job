# MANIFEST — Burn Job Performance Refactoring Engine

## 1. Заявленный уровень (Level)

- **Уровень**: `hard`
- **Описание уровня**: артефакт не только строит статический и динамический
  граф-анализ с выгрузкой машиночитаемых находок `findings.json`, но и
  автоматически генерирует нагрузочный сценарий (`loadtest/`), выполняет
  итеративный рефакторинг исходного Java-кода через LLM-агента и
  верифицирует сохранность контрактов с замером метрик «до»/«после».

## 2. Состав артефакта

- **Тип артефакта**: `skill` + `CLI pipeline`.
- **Как подключается**: точка входа — консольная команда `burn-job`
  (устанавливается через `pip install -e .`, см. `RUN.md`). Манифест умения
  для агента — `skill/SKILL.md`.
- **Структура**:
  - `skill/SKILL.md` — манифест возможностей артефакта для подключения к агенту.
  - `src/burn_job/` — движок: детекторы T1–T9 (`detectors/`), граф-БД KùzuDB
    (`graph/`), 8-этапный пайплайн (`pipeline/`), LLM-агент рефакторинга
    (`refinement/`), генератор отчётов (`report/`).
  - `run.sh`, `RUN.md` — воспроизводимый запуск с нуля.
  - `reports/sandbox/` — `findings.json` + `report.md` по результатам прогона.
  - `reports/control/` — не заполняется: control-проект команде пока не выдан
    (заполняется только при получении control, согласно `SUBMISSION.md`).
  - `loadtest/`, `measurements/`, `runlog/`, `pr/` — генерируются/заполняются
    прогоном артефакта на `test_project` (см. раздел «Статус» ниже).

## 3. Декларация ручных правок

- **Правки находок/кода**: `0%` — все находки (`findings.json`), варианты
  исправлений и применённые правки в `test_project/src/main/java`
  производятся исключительно движком `burn_job` (детекторы → LLM-варианты →
  бенчмарк → выбор победителя → `mvn test-compile`), без ручного
  редактирования дефектов человеком.
- **Ручная работа, выполненная человеком**: только подготовка окружения —
  установка Maven/JDK, поднятие локального PostgreSQL, выдача API-ключа
  DeepSeek. Это не относится к анализу/правкам кода, а является
  предварительным разворачиванием инструментов согласно `RUN.md`.

## 4. Изменения конфигурации и pom.xml

- **`spring.jpa.open-in-view`**: не изменялось, зафиксировано `false` как
  требует регламент.
- **`test_project/pom.xml`**: добавлена runtime-зависимость
  `org.postgresql:postgresql`. **Обоснование**: `application-load.yaml`
  требует подключения к реальному PostgreSQL (`jdbc:postgresql://localhost:55432/postgres`),
  но исходный `pom.xml` содержал только H2-драйвер — без добавленной
  зависимости `load`-профиль не может подняться вообще, независимо от
  какой-либо оптимизации. Изменение не влияет на измеряемую
  производительность, только позволяет профилю запуститься.
- Прочие зависимости и плагины `pom.xml` не тронуты.

## 5. Внешние зависимости для прогона

- **Python**: `>= 3.10`; пакеты `kuzu`, `jinja2`, `llama-cpp-python`
  (опционально, для локального инференса), `typer`, `rich`, `pytest`.
- **Java JDK**: `21` (требование `test_project/pom.xml`; JDK 17 недостаточно —
  в коде используются records/pattern matching/switch expressions Java 21).
- **Apache Maven**: `>= 3.8` (заявлено `README.md`; фактически проверялось на `3.6.3`).
- **PostgreSQL**: локальный инстанс, слушающий `localhost:55432`,
  роль/БД `postgres`/`postgres` (для `load`-профиля `test_project`).
- **DeepSeek API key**: `DEEPSEEK_API_KEY` в `.env` (платно, генерация
  LLM-вариантов исправлений).

## 6. Статус на момент этой версии MANIFEST.md

Документация и структура репозитория приведены в соответствие с
`SUBMISSION.md`. Реальный прогон 8-этапного цикла на `test_project` **ещё не
выполнен в этом окружении** — заблокирован отсутствием JDK 21 (на машине
установлены только 11 и 17; установка требует `sudo`, ожидает выполнения
пользователем). После установки JDK 21 и запуска `burn-job run-cycle --apply`
по `RUN.md`, разделы `reports/sandbox/`, `loadtest/`, `measurements/`,
`runlog/`, `pr/` будут заполнены реальными данными без ручного вмешательства.
