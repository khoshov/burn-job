# Feature Specification: Автоматизированный контур профилирования, анализа и авто-исправления производительности Java бэкенда

**Feature Branch**: `001-automated-performance-optimization-pipeline`

**Created**: 2026-07-28

**Status**: Clarified (Ready for Planning)

**Input**: User description: "У нас есть исходный код проекта (бэкенд на java). Мы генерируем для него api тесты (небольшая нагрузка запускаем несколько раз). Получаем отчёт микрометр. Формируем JFR под этими же api тестами. Детектим проблемы и записываем результаты в графовую базу. Запускаем агента с задачей на улучшения. Прогоняем тесты ещё раз, смотрим метрики, запускаем ещё одну итерацию, прогоняем несколько раз, выбираем лучший результат и применяем результаты в коде."

---

## 1. Clarified Architecture & Technical Decisions

- **Генератор API-тестов**: Динамический парсер/генератор на основе анализа OpenAPI и Spring REST контроллеров (`@RestController`), формирующий Python/k6 нагрузочные сценарии (`generate_api_loadtests.py`).
- **Движок профилирования**: Встроенный HTTP-агент `async-profiler` (`ap-loader` / `ProfilerController`), позволяющий управлять сбором CPU/Memory сэмплов во время выполнения нагрузочного прогона без перезапуска JVM.
- **Scoring Function (Формула оценки варианта)**:
  $$\text{Score} = 0.6 \times \Delta\text{Latency}_{p95} + 0.3 \times \Delta\text{RPS} + 0.1 \times \Delta\text{GC Allocations}$$
  Вариант с максимальным положительным итоговым баллом признается победителем (Winner).
- **Стратегия бенчмаркинга и приложения правок**:
  - *Итеративная фаза:* Переключение вариантов через In-Memory Feature Toggles (`?variant=v1|v2|v3`) на лету (< 50 мс) без перезапуска JVM и без повторной пересборки.
  - *Финализация:* Атомарная замена кода исходного Java-файла репозитория с обязательным прогоном regression tests (`mvn test`).

## 2. User Scenarios & Testing *(mandatory)*

### User Story 1 - Генерация и запуск API-тестов под сопутствующий сбор метрик Micrometer и JFR (Priority: P1)

Как инженер по производительности или CI/CD система, я хочу автоматически анализировать Spring `@RestController` эндпоинты и генерировать нагрузочные сценарии с параллельным снятием Micrometer-метрики и JFR/collapsed профилей.

**Why this priority**: Без автоматического анализа контроллеров и воспроизводимой нагрузки невозможно точно измерить задержки (latency), пропускную способность (RPS) и снять валидные профили стек-трейсов вызовов JVM.

**Independent Test**: Запуск генератора `skill/scripts/generate_api_loadtests.py` против работающего Spring Boot приложения с одновременным вызовом `POST /api/profiler/profile?duration=X` и сбором отчетов `micrometer_report.json` и `profile.collapsed`/`.jfr`.

**Acceptance Scenarios**:
1. **Given** запущенное Java бэкенд приложение (Spring Boot 3 + Actuator/Micrometer + ProfilerController), **When** запускается динамо-генерация и исполнение API-тестов под нагрузкой, **Then** система находит эндпоинты контроллеров и исполняет контролируемый поток HTTP-запросов.
2. **Given** прогон API-тестов, **When** сессия нагрузочного тестирования завершается, **Then** сохраняются:
   - JSON-отчет с метриками Micrometer (Latency p50/p95/p99, throughput/RPS, error rate).
   - JFR профиль (`.collapsed`/`.jfr` файл профилирования вызовов CPU и аллокаций памяти).

### User Story 2 - Детекция проблем производительности и сохранение в графовую базы данных (KùzuDB) (Priority: P1)

Как аналитическая система, я хочу распознавать антипаттерны производительности (N+1 SQL-запросы, In-memory фильтрация/пагинация, отсутствие пакетирования при saveAll, избыточная загрузка LOB/сущностей) на основе JFR-профилей и метрик, сохраняя граф вызовов и найденные проблемы в графовую БД (KùzuDB).

**Why this priority**: Графовое представление со связями `(Method)-[:CALLS]->(Query)` и `(Method)-[:HAS_DEFECT]->(Issue)` позволяет AI-агенту локализовать точное место в исходном Java-коде и понять контекст вызова с задержкой за < 50 мс.

**Independent Test**: Передача сформированного профиля в `jfr_to_graph.py` / `static_pattern_detectors.py`, проверка создания узлов `Method`, `Class`, `Issue` и связей в графовом файле `profiler_graph.db`.

**Acceptance Scenarios**:
1. **Given** JFR/collapsed профиль и Micrometer-отчет приложения под нагрузкой, **When** запускается графовый инджестинг и статические/динамические детекторы таксономии (T1–T9), **Then** в KùzuDB формируется топология вызовов и создаются объекты найденных дефектов со ссылками на имена Java-классов и методов.
2. **Given** обнаруженный антипаттерн (например, N+1 в `NPlusOneService.getDepartmentsSubOptimal`), **When** выполняется Cypher-запрос к графу, **Then** возвращается точная контекстная справка: имя файла, строки, тип проблемы и сопутствующие вызовы Hibernate/JDBC.

### User Story 3 - Генерация вариантов оптимизации Java-кода LLM-агентом (Priority: P1)

Как автоматизированный оптимизатор, я хочу передавать контекст из графовой базы и исходные Java-файлы в LLM-агент (`llm_agent.py`), чтобы получать 1 или несколько гипотез (вариантов) оптимизации кода (`v1`, `v2`, `good`).

**Why this priority**: Ручной рефакторинг замедляет процесс. Автономный агент рефакторинга (`llm_agent.py`) генерирует целевые изменения (JOIN FETCH, DTO-проекции, Spring Data Pageable, Batch inserts).

**Independent Test**: Запуск `llm_agent.py --report findings.json` возвращает валидный вариант решения, создающий модифицированный Java-код или Feature Toggle варианты.

**Acceptance Scenarios**:
1. **Given** сформированный структурированный отчет о проблемах из KùzuDB, **When** вычисляется промпт и передается в LLM-агент, **Then** агент генерирует рефакторинг кода (например, замена `.findAll().stream().filter()` на JPQL `@Query` с фильтрацией на стороне СУБД).
2. **Given** сгенерированный вариант оптимизации, **When** запускается автоматическая компиляция (`mvn test-compile`), **Then** код успешно компилируется без синтаксических ошибок.

### User Story 4 - Итеративное мульти-вариантное тестирование через Feature Toggles и сравнение метрик (Priority: P2)

Как система управления оптимизацией, я хочу проводить мгновенное циклическое тестирование каждого предложенного варианта кода (`v1`, `v2`, `v3`) в памяти через Feature Toggles без перезапуска JVM, снимать повторные Micrometer & JFR метрики и сравнивать их с baseline.

**Why this priority**: Тестирование вариантов в памяти без перезапуска приложения занимает < 1 сек на итерацию и полностью исключает накладные расходы на холодный запуск JVM.

**Independent Test**: Запуск `benchmark_variants.py` / `iterative_agent_loop.py`, приводящий к генерации сравнительной таблицы/отчета дельт метрик по формуле Scoring Function.

**Acceptance Scenarios**:
1. **Given** N сгенерированных вариантов оптимизации, **When** запускается итеративный бенчмарк с передачей HTTP-параметров `?variant=vN`, **Then** приложение исполняет соответствующую ветку кода без пересборки.
2. **Given** результаты замеров для каждого варианта, **When** вычисляется значение Scoring Function ($0.6 \Delta\text{Latency}_{p95} + 0.3 \Delta\text{RPS} + 0.1 \Delta\text{GC}$), **Then** формируется итоговый ранжированный список вариантов.

### User Story 5 - Выбор лучшего результата (Winner) и физическая финализация в коде (Priority: P2)

Как главный оркестратор контура, я хочу автоматически выбирать наилучший вариант по максимальному балу Scoring Function и физически подставлять его код в файлы исходного Java-кода в репозитории с последующим перезапуском integration tests.

**Why this priority**: Обеспечивает сквозную (end-to-end) автономию — от выявления узкого места до изменения файлов репозитория.

**Independent Test**: Полный прогон `run_full_autonomous_cycle.py`, результатом которого является обновление исходных `.java` файлов целевыми оптимизированными файлами и прохождение `mvn test`.

**Acceptance Scenarios**:
1. **Given** завершенные итерации бенчмарков для нескольких вариантов, **When** вариант $V_{\text{winner}}$ получает максимальный Score, **Then** он утверждается к финализации.
2. **Given** сгенерированный код Winner-варианта, **When** финализируется этап, **Then** код атомарно перезаписывает целевой `.java` файл в `src/main/java/...`, и запускается `mvn test` для финальной проверки отсутствия регрессий.

### Edge Cases

- **Нестабильное приложение при нагрузке**: Если бэкенд возвращает 5xx или падает под нагрузкой, цикл генерации тестов приостанавливается, а ошибка фиксируется в отчете без зацикливания.
- **Ошибки компиляции сгенерированного LLM кода**: Если `llm_agent` выдает синтаксически невалидный Java-код, вариант отбраковывается с записью лога компиляции, и запускается повторная попытка генерации.
- **Отсутствие прироста производительности**: Если ни один вариант не показал улучшения по формуле Scoring Function, исходный код остается неизменным, и выводится предупреждение.
- **Недоступность LLM API**: В случае отсутствия интернет-соединения или API ключа, система переключается в локальный детерминированный режим (Offline Taxonomy Rule Engine).

## 3. Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА динамически сканировать `@RestController` аннотации для генерации API-нагрузочных сценариев.
- **FR-002**: Нагрузочный генератор ДОЛЖЕН выполнять многократные серии HTTP-запросов с настраиваемыми параметрами параллелизма (`concurrency`) и количества запросов.
- **FR-003**: Модуль профилирования ДОЛЖЕН собирать метрики выполнения через Micrometer / Spring Actuator (latency p50/p95/p99, RPS, error count).
- **FR-004**: Модуль профилирования ДОЛЖЕН активировать сбор профилей через async-profiler REST API (`ProfilerController`) во время исполнения API-тестов.
- **FR-005**: Графовый модуль ДОЛЖЕН парсить стектрейсы профилей и заносить граф вызовов методов и SQL-запросах в KùzuDB.
- **FR-006**: Модуль детекции ДОЛЖЕН автоматически классифицировать антипаттерны Hibernate/JPA:
  - N+1 Query Problem (T1)
  - In-Memory Filtering / Pagination (T2)
  - Save in Loop / Missing JDBC Batching (T3)
  - Full Entity Fetch instead of Projection (T4)
- **FR-007**: AI-агент ДОЛЖЕН принимать граф проблем и код методов, генерируя варианты исправления на Java 21.
- **FR-008**: Контур ДОЛЖЕН поддерживать мульти-вариантное тестирование правок в памяти через Feature Toggles без перезапуска JVM.
- **FR-009**: Сравнительный модуль ДОЛЖЕН вычислять результат по формуле Scoring Function: $0.6 \Delta\text{Latency}_{p95} + 0.3 \Delta\text{RPS} + 0.1 \Delta\text{GC}$.
- **FR-010**: Оркестратор ДОЛЖЕН автоматически выбирать лучший вариант (Winner) на основе максимального бала Scoring Function.
- **FR-011**: Система ДОЛЖНА атомарно применять код Winner-варианта в файлы исходного Java-кода репозитория.
- **FR-012**: После применения оптимизаций система ДОЛЖНА выполнять интеграционные тесты Maven (`mvn test`) для гарантии сохранения функциональной корректности.

## 4. Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полный цикл (динамо-нагрузка → async-profiler → KùzuDB → LLM Agent → итерации в памяти → выбор Winner → финализация в файле) выполняется полностью автоматически.
- **SC-002**: Сокращение Latency p95 для целевых оптимизированных эндпоинтов минимум на **40%** по сравнению с исходным кодом.
- **SC-003**: Прирост пропускной способности (RPS) на оптимизированных эндпоинтах минимум на **50%**.
- **SC-004**: Время итерации оценки вариантов в памяти за счет Feature Toggles не превышает **200 мс**.
- **SC-005**: 100% сохранение функциональной корректности (все существующие integration/unit тесты `mvn test` проходят успешно после замены файлов).

---

## 5. Assumptions

- Проект использует Java 21, Spring Boot 3.3+, Spring Data JPA / Hibernate ORM.
- Приложение предоставляет REST API с возможностью сбора метрик Micrometer и встроенным `ProfilerController` (ap-loader).
- Для хранения графа вызовов и антипаттернов используется встраиваемая графовая СУБД KùzuDB.
- Для рефакторинга кода используется LLM-агент (`llm_agent.py`), подключаемый через API (DeepSeek / OpenAI / GigaChat) или работающий в детерминированном fallback-режиме offline rules.
