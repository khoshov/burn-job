# SUBMISSION — формат сдачи работы

## Структура

```
<команда>/
├── MANIFEST.md              уровень (soft|hard), состав артефакта, что делалось руками
├── skill/                   сам артефакт: skill / MCP-tool / workflow / rules
├── RUN.md                   как запустить ваш артефакт с нуля, включая установку зависимостей
├── reports/
│   ├── sandbox/
│   │   ├── report.md        человекочитаемый отчёт
│   │   └── findings.json    машинночитаемые находки (схема ниже)
│   └── control/             заполняется, только если вам выдавали control
├── loadtest/                ваш нагрузочный тест (обязателен для hard)
├── measurements/            сырые артефакты замеров: снапшоты метрик, .jfr, вывод ab
├── pr/                      патч или ссылка на PR с правками
└── runlog/                  лог работы артефакта: что он читал, что предлагал, что менял
```

## Как это будет судиться

**Менять в работе можно что угодно.** Но перед замером судья восстанавливает из эталонного тега
`src/test/**`, `harness/`, `scripts/`, `judge/` и данные сида, а из вашей работы берёт
**только `src/main/**`, `pom.xml` и конфигурацию**.

Практический вывод: правки тестов, измерительной обвязки, скриптов и объёма сида до замера не доживут.
Если ваш фикс работает только вместе с изменённым тестом или уменьшенным объёмом данных — он не будет засчитан.

**`spring.jpa.open-in-view` менять запрещено.** Зафиксировано `false`. Изменение аннулирует замер
по этому сету, прогон повторяется на эталонной конфигурации.

Итог считается по двум сетам: `sandbox × 0.3 + control × 0.7`, тай-брейк по `control`.

## MANIFEST.md

Обязательно укажите:

- **уровень**: `soft` или `hard`;
- состав артефакта и как он подключается;
- **что делалось руками, а не артефактом** — честное перечисление. Ручная работа допустима,
  необъявленная ручная работа штрафуется;
- любые изменения конфигурации и `pom.xml` с обоснованием;
- внешние зависимости, которые нужно поставить перед прогоном.

## Схема findings.json

```json
{
  "set": "sandbox",
  "level": "hard",
  "findings": [
    {
      "file": "src/main/java/ru/hackathon/profiling/sensorhub/service/report/DailyReportService.java",
      "line_from": 53,
      "line_to": 61,
      "family": "db",
      "pdf_taxonomy": ["T6", "T2"],
      "mechanism": "коллекция измерений инициализируется отдельным запросом на каждую станцию",
      "impact": "число обращений к базе растёт линейно по числу станций",
      "fix": "выбрать станции вместе с измерениями одним запросом либо агрегировать в базе",
      "evidence": {
        "channel": "X-Sql-Count",
        "before": 2001,
        "after": 1,
        "how": "GET /api/reports/daily?from=2026-06-01&to=2026-06-30, профиль load, один вызов"
      }
    }
  ],
  "checked_but_not_an_issue": [
    {
      "file": "src/main/java/ru/hackathon/profiling/sensorhub/service/report/DailyRow.java",
      "claim": "порядок полей выглядит неоптимальным",
      "why_not": "измерено JOL: размер объекта не изменился, 40 байт против 40"
    }
  ]
}
```

### Обязательные поля

| Поле | Когда обязательно | Комментарий |
|---|---|---|
| `file` | всегда | путь от корня проекта |
| `line_from` | всегда | строка, с которой начинается дефект |
| `family` | всегда | одно из: `db`, `cpu`, `memory`, `algo`, `redundant` |
| `pdf_taxonomy` | всегда | список кодов `T1`–`T9` |
| `mechanism` | всегда | **почему** это дорого, одним предложением. Не «медленный код», а механизм |
| `fix` | всегда | что предлагается сделать |
| `evidence.before` / `evidence.after` | для `hard` | измеренные числа |
| `evidence.channel` | для `hard` | по какому каналу видно: `X-Sql-Count`, `X-Elapsed-Ms`, `jvm.memory.used`, `jvm.memory.usage.after.gc`, JFR |
| `evidence.how` | для `hard` | как воспроизвести замер: эндпоинт, параметры, профиль |

Находка без `mechanism` засчитывается как неполная: «здесь тормозит» — это не находка.

### Раздел `checked_but_not_an_issue`

Сюда пишите то, что вы проверили и сознательно **не** сочли дефектом.

Важно: **баллов этот раздел не даёт и бонуса за точность не даёт.** Его единственная функция —
защитить вас от штрафа за ложную находку, если вы упомянули место, которое дефектом не является.
Упомянули с обоснованием — штрафа нет. Заявили как дефект — штраф.

Перед тем как заявить находку, сверьтесь с разделом 7 «Чего мы не считаем дефектом»
в `coding-standards.md` проекта. Там перечислено то, что в этом проекте дефектом не считается,
и указано почему.

## Что снижает балл

- ложная находка: заявлено как дефект то, что дефектом не является;
- красные тесты после ваших правок;
- изменённый контракт API;
- «оптимизация» удалением функциональности;
- невоспроизводимые числа: заявлено «стало быстрее», но по описанию замер не повторяется;
- правила, захардкоженные под конкретный проект (имена классов песочницы в коде артефакта);
- необъявленные ручные правки.

Точные веса и величины штрафов — в рубрике, она публикуется вместе с результатами.

## Как повысить балл

- измеряйте, а не рассуждайте: `before`/`after` с указанием канала и способа воспроизведения;
- классифицируйте по таксономии — верная категория оценивается отдельно;
- покрывайте разные семейства дефектов, а не пять вариаций одного;
- пишите механизм: судья должен понять причину из одной строки;
- атомарные коммиты в PR: один дефект — один коммит.
